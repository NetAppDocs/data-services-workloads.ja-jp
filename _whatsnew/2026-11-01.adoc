=== Workload Factoryの管理機能強化



==== カスタムダッシュボードのデータを確認して更新します

カスタムダッシュボードの指標が最後に更新された日時を確認したり、手動で更新したりできるようになりました。「データの更新」にカーソルを合わせると、最終更新日時が表示されます。

*データの更新* を選択して、新しいスキャンを開始します。スキャンが開始されたことを示すバナーが表示され、スキャンが完了するまでボタンは無効になります。

新しいデータが利用可能になったら、通知バナーの*今すぐ読み込む*を選択してダッシュボードを更新してください。

「データの更新」と「今すぐ読み込む」の両方で、Tracker にデータ収集イベントが作成されます。

link:https://docs.netapp.com/us-en/data-services-workloads/admin/manage-custom-dashboards-fsx.html#refresh-dashboard-data["カスタムダッシュボードデータを更新する方法を確認する"]



==== カスタムダッシュボードのリージョンを指定します

カスタムダッシュボードでは、リクエストに含まれていない地域を1つ以上選択するよう求められるようになりました。ダッシュボードのデータは、選択した地域に限定されます。

link:https://docs.netapp.com/us-en/data-services-workloads/admin/create-custom-dashboard-fsx.html["カスタムダッシュボードの作成方法を学習します"]



==== FSx for ONTAP リンク作成の IAM ポリシー

リンクを作成するためのCloudFormationテンプレートとTerraformコードでは、インラインのLambda権限ではなく、IAMポリシーを使用するようになりました。

link:https://docs.netapp.com/us-en/data-services-workloads/fsx-storage/create-link.html["リンクの作成方法を学ぶ"]



==== AIエージェントの動作に関する監査と追跡

Tracker を使用して、AIエージェント設定の変更と、読み取り / 書き込みモードでの各承認リクエスト（エージェントの質問とユーザーの回答を含む）を確認できるようになりました。

Workload Factory APIを介して行われたリソースの変更は、その操作を実行するWorkload Factoryサービスがログに記録します。

link:https://docs.netapp.com/us-en/data-services-workloads/admin/learn-agent.html["エージェントのアクションの監査と追跡について学ぶ"]

=== Amazon FSx for NetApp ONTAPの機能強化



==== イニシエータグループ図の改良

「クライアントアクセス管理」ページに表示される、ブロックデバイスのイニシエータグループを示す図に、ホストに関する詳細情報が追加されました。図中のホストにカーソルを合わせると、ホスト名、インスタンスID、ワークロードタイプ、リージョン、iSCSI修飾名（IQN）などのホストの詳細が表示されます。



==== Well-Architectedの問題に対するメール機能の強化

新しいメールデザインでは、Workload Factoryが検出した構成上の問題について、より詳細な情報とコンテキストを提供します。メールには、分析されたリソースの数、警告または重大な問題があるリソースの数、およびそれらの問題の内容が記載されています。また、このメールにはFSx for ONTAPのWell-Architectedダッシュボードへのリンクも記載されているため、問題をすぐに解決できます。



==== 優れた設計のダッシュボード機能強化



===== 選択された構成チェックのサポート

選択した構成に対して手動で分析を実行することで、関心のある構成のみを分析し、待ち時間を短縮できます。



===== 優れたアーキテクチャ分析における新たな推奨事項

Workload Factory は、FSx for ONTAP ファイルシステムの適切なアーキテクチャ分析に以下の構成を含めるようになりました：

ストレージワークロードの場合：

* *ホストをフェイルオーバーノードに接続*：信頼性を確保するため、アクティブ / パッシブのFSx for ONTAPファイルシステムでホストがフェイルオーバーノードに接続されているかどうかを確認します。
* *ホストを優先ノードに接続*：ホストがパフォーマンス効率のために優先ノードを使用してブロックデバイスに接続されているかどうかを確認します。
* *ARP/AIの複数デバイス検出のギャップ*：ボリュームにブロックデバイスが1つだけ接続されている場合に、ARP/AIは完全な保護範囲を提供します。ボリュームに複数のブロックデバイスが接続されている場合、Workload Factoryはブロックデバイスを新しいボリュームに移動し、各ボリュームにブロックデバイスが1つだけ存在するようにします。
* *クローンクリーンアップ*：ストレージ使用量を最適化し、コストを削減するために削除できる、30日以上前のボリュームクローンがあるかどうかを確認します。
* *igroup OSとホストの一致*：イニシエータグループ（igroup）のオペレーティングシステムがホストのオペレーティングシステムと一致しているかどうかを確認し、I/Oやパフォーマンスの問題を防止します。


Kubernetesワークロードの場合：

* *QoS設定*：パフォーマンス効率を高めるために、Kubernetesの永続ボリュームがONTAP QoSポリシーで保護されているかどうかを確認します。
* *専用KubernetesストレージVM*：ファイルシステムがKubernetesワークロードに専用のストレージVMを使用しているかどうかを確認し、分離性を向上させ、ストレージ管理を簡素化します。
* *専用のKubernetesエクスポートポリシー*：各Kubernetes永続ボリュームに、クラスターのワーカーノードからのアクセスのみを許可する専用のエクスポートポリシーがあるかどうかを確認します。
* *Kubernetes iSCSIバックエンドの双方向CHAP*：Trident iSCSIバックエンドでセキュリティのために相互CHAP認証が有効になっているかどうかを確認します。
* *アプリケーションストレージVMでの `showmount`の無効化*：クライアントがアクセスできないエクスポートを一覧表示するのを防ぐため、アプリケーションストレージVMで `showmount`が無効になっているかどうかを確認します。


データベースワークロードの場合：

* *SAP HANAスナップショットポリシー*：アクティブなデータベースデータのストレージコストを削減し、パフォーマンスを向上させるために、SAP HANAボリュームのスナップショットポリシーが「なし」に設定されているかどうかを確認します。
* *MySQLスナップショットポリシー*：アクティブなデータベースデータのストレージコストを削減し、パフォーマンスを向上させるために、MySQLボリュームのスナップショットポリシーが「なし」に設定されているかどうかを確認します。
* *PostgreSQLスナップショットポリシー*：アクティブなデータベースデータのストレージコストを削減し、パフォーマンスを向上させるために、PostgreSQLボリュームのスナップショットポリシーが「なし」に設定されているかどうかを確認します。




===== 構成の現在の値と推奨値

適切に設計されたダッシュボードでは、最適化されていない一部の構成について、現在の値と推奨値を確認できます。これは、修正する前に推奨される値を示しています。

* コールドデータ階層化
* Snapshot ポリシー
* SSDの容量余裕




==== コスト改善



===== コスト予測と分析

コスト予測機能を使用して、FSx for ONTAPファイルシステムのコストを予測できるようになりました。これは、予算計画を立て、リソースを効果的に最適化するのに役立ちます。また、コストや利用パターンに関する分析結果を確認することで、コスト最適化の機会を特定することもできます。



===== AWS コストおよび使用状況レポート（CUR）

Workload Factoryは、お客様所有のS3バケットに配信される詳細な請求記録を提供するために、AWS Cost Explorerの代わりにAWS Cost and Usage Reports（CUR）を使用するようになりました。CURはより詳細なコスト情報を提供し、高度なFinOps、チャージバック、およびコスト配分のユースケースの基盤として機能します。



==== ストレージVM移行の改善

Workload Factoryは、ストレージVMの移行に関して、ユーザーインターフェース内でより詳細なガイダンスを提供します。これには、移行を本番環境に導入する前に、段階的な手順説明とテスト実行が含まれます。

link:fsx-storage/create-replication.html["ストレージVM移行について詳しくはこちらをご覧ください"]



==== レプリケーション遅延メール通知の改善

関連するレプリケーション遅延イベントが多数発生した場合、Workload Factoryはそれらを自動的に1つのメール通知に統合するため、通知が多すぎて混乱することはありません。



==== 自動容量管理機能の強化

Workload Factoryに容量の自動管理を依頼する前に、自動容量管理通知を有効にして機能を試用できるようになりました。ファイルシステムの容量が少なくなると、通知されます。



==== 適切に設計されたダッシュボードに含まれるデータベース構成

適切に設計されたダッシュボードには、データベース構成に関する推奨事項が含まれるようになり、ベストプラクティスに基づいて設定を評価および最適化できるようになりました。ダッシュボードに含まれる最初の設定項目は以下のとおりです：

* コールドデータ階層化
* ストレージ効率
* Snapshot ポリシー
* SSDの容量余裕
* ブロックデバイスのスペース管理
* OS タイプ
* ブロックデバイスのOSタイプをホストと一致させる
* 非アクティブなブロックデバイス（LUN）
* データファイル（.mdf）の配置
* ログファイル（.ldf）の配置
* マルチパスI/Oステータス
* マルチパスI/Oタイムアウト
* クラスタークォーラム
* コンピューティングリソースの最適化


Workload Factoryコンソールでメインメニューを選択し、次に*Well-architected*を選択してWell-architectedダッシュボードを見つけます。

image:well-architected-menu-option.png["Workload Factory コンソールの Well-architected メニューオプション"]



==== スループット決定ポイント

クライアントのスループットに関する推奨事項と、自動化の判断ポイントを確認できるようになりました。判断ポイントにカーソルを合わせると、現在のSKUと推奨SKU、または一定期間内に違反した指標（％）などの詳細情報が表示されます。



[[workload-factory-for-vmware-enhancements]]
=== Workload Factory for VMwareの機能強化

これらの機能強化は、VMware移行向けのEVS TCO計算ツールを対象としています。



==== EVS TCO 計算ツールにおける i7i.metal-24xl および i7i.metal-48xl インスタンスのサポート

EVSのTCO計算ツールが、クラスターホストとしてAWSのi7i.metal-24xlおよびi7i.metal-48xl EC2インスタンスをサポートするようになりました。i4i.metal構成と比較して、i7i.metal-24xlインスタンスは、コンピューティングのEVS初期コストを約33%、vSANストレージのEVS初期コストを約25%削減します。

この計算ツールは、すべてのインスタンスタイプを比較し、最もコストの低いオプションを自動的に選択します。新しい比較セクションでは、EVSホストの構成を並べて表示することで、ニーズに最適な設定をより簡単に選択できます。

link:https://docs.netapp.com/us-en/data-services-workloads/fsx-vmware/calculate-evs-savings.html["EVSの推定節約額を計算する"]



[[workload-factory-for-eda-enhancements]]
=== Workload Factory for EDAの機能強化

これらの機能強化には、レイテンシー分析におけるボリュームの詳細、ファイルシステムの負荷チェック、スループットの判断ポイント、およびレイテンシー分析の再実行が含まれます。



==== レイテンシー分析中にボリュームの詳細を表示します

レイテンシイベントを分析する際に、Workload Factoryでボリュームの詳細を表示することで、ボリュームがどのように構成されているかを確認できます。詳細レイテンシ分析ページには、*ボリュームタイプ*（RWまたはDP）と*ボリュームスタイル*（FlexVolまたはFlexGroup）が表示されます。

link:https://docs.netapp.com/us-en/data-services-workloads/fsx-eda/task-analyze-latency-trends.html["レイテンシの傾向を分析する方法を学ぶ"]



==== レイテンシイベントのファイルシステムの負荷を確認する

Workload Factoryでは、レイテンシイベントが発生した際にファイルシステムの負荷がパフォーマンスに影響を与えたかどうかを確認できるため、ファイルシステムを調査するかどうかを判断できます。レイテンシアラートが発生しているボリュームについては、イベント発生前の40分間のCloudWatchデータを表示し、ファイルシステムを開いてさらに調査することができます。

link:https://docs.netapp.com/us-en/data-services-workloads/fsx-eda/learn-latency-monitoring.html#file-system-pressure["ファイルシステムの負荷チェックについて"]



==== EDAのスループット決定ポイントを確認する

EDA概要ダッシュボードでクライアントのスループット決定ポイントを確認することで、Workload Factoryがスループットの変更を推奨または適用したタイミングを確認できます。決定ポイントにカーソルを合わせると、現在のSKUと推奨SKU、または指定した期間内に違反した指標などの詳細が表示されます。

link:https://docs.netapp.com/us-en/data-services-workloads/fsx-eda/task-use-overview-dashboard.html#analyze-capacity-and-throughput-trends-and-decision-points["スループット決定ポイントのレビュー方法"]



==== レイテンシ分析を再度実行する

Workload Factoryでは、ボリュームに対してレイテンシ分析を再度実行することで、調査や変更後に結果を更新できます。*分析を再度実行*を選択すると、新しい分析が開始され、結果が更新されます。

link:https://docs.netapp.com/us-en/data-services-workloads/fsx-eda/task-analyze-latency-issues.html["レイテンシの問題を分析する方法について学習します"]

[[oci-netapp-storage-service-enhancements]]
=== OCI NetApp ストレージサービスの強化



==== OCI NSSシステムの適切に設計された分析

NetApp Workload Factoryには、OCI NSSシステム向けの適切に設計された評価機能が含まれています。この評価では、業務効率の向上に役立つ洞察、推奨事項、および改善策を提供します。

OCI Well-Architected Frameworkの以下の柱について、構成評価が利用可能です：

* 信頼性：ファイルオブジェクト容量、スナップショットポリシー、およびSSD容量の余裕
* 運用上の卓越性：ホストから認識可能な容量レポートとボリューム容量のヘッドルーム
* コスト最適化：コールドデータ階層化、スナップショットクリーンアップ、ストレージ効率化


link:https://docs.netapp.com/us-en/data-services-workloads/oci/add-credentials-oci.html["OCI NSSシステムの適切に設計された分析"]およびlink:https://docs.netapp.com/us-en/data-services-workloads/oci/improve-configurations.html["適切に設計された構成を実装する"]の詳細をご覧ください。
